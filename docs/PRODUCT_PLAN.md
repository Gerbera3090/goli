# 고리 제품 기획

> 상태: 2026-08-20 기준 초안. 현재 구현과 최종 제품 계획을 구분해 기록한다.

## 제품 정의

고리는 KAIST 구성원과 교내 단체가 기억하기 쉬운 짧은 링크를 만들고, QR과
접속 통계를 관리하며, 링크 모음 페이지를 운영할 수 있게 하는 서비스다.

- 서비스명: 고리 (GOLI)
- 최종 공개 주소: `gori.sparcs.org`, `goli.sparcs.org`
- 임시 프리뷰 주소: `gori.bera.page`, `gori2.bera.page`
- 핵심 사용자: KAIST 개인 구성원, 동아리, 학생단체 및 기타 교내 모임

두 공개 주소는 같은 slug와 목적지를 제공한다. `gori2.bera.page`는 보조 주소
동작을 검증하기 위한 프리뷰 도메인이며 최종 브랜드 주소가 아니다.

## URL 원칙

짧은 링크에는 `/go`를 붙이지 않고 루트 경로를 사용한다.

```text
https://gori.sparcs.org/2026고리홍보
https://goli.sparcs.org/2026고리홍보
```

서비스 관리 화면은 반드시 `/manage` 아래에 둔다.

```text
/manage/links
/manage/linktree
```

slug는 한글, 영문 소문자, 숫자, `_`, `-`를 허용한다. 현재 예약어는 `_next`,
`api`, `go`, `manage`이며 기능 경로가 추가될 때 함께 갱신한다. slug는 전체
서비스에서 유일하다.

## 기능 범위

### 1. 짧은 링크와 QR

- 사용자 지정 slug와 자동 생성 slug
- 동일 slug를 두 공개 도메인에서 제공
- 링크 생성, 조회, 수정, 비활성화 및 소유권 이관
- 링크별 QR 생성과 다운로드
- MySQL unique constraint를 최종 중복 방지 수단으로 사용
- 경합이 잦은 slug 생성에는 Redis 분산 락을 추가
- 서비스 경로 및 금지어를 예약어로 차단

짧은 링크를 열면 목적지 URL과 이동 버튼이 있는 확인 페이지를 먼저 보여준다.
사용자가 버튼을 눌러 이동하므로 브라우저 뒤로가기에 확인 페이지가 남는다.
사용자 동작 없는 자동 리다이렉트는 브라우저가 히스토리에서 건너뛸 수 있어
사용하지 않는다.

### 2. 접속 로그와 통계

- 링크별 총 접속 수
- 날짜 및 시간대별 접속량
- 원본 로그와 집계 데이터의 보존 기간 분리
- 관리 화면에서 기간별 추이 제공
- 운영자와 소유자가 비정상 접속을 구분할 수 있는 최소 정보 제공

수집 항목, 익명화 방식, 보존 기간은 개인정보 검토 후 확정한다.

### 3. 링크트리

- 개인 또는 단체의 공개 링크 모음 페이지
- 링크 순서, 제목, 설명, 활성 상태 관리
- 링크별 접속 통계
- 관리 경로는 `/manage/linktree`

### 4. 단체

- 개인 링크와 단체 링크를 함께 지원
- 링크에는 생성자 `userId`와 소유 단체 `orgId`를 기록
- 개인 소유 링크는 `orgId`를 비워 둠
- 단체 관리자 추가, 권한 회수, 대표 관리자 및 소유권 이관
- KAIST 동아리는 Clubs와 gRPC로 연동
- 총학생회 산하단체, 동호회 등은 커스텀 단체로 등록
- 필요할 때 gRPC Gateway를 열어 HTTP 클라이언트도 지원

Clubs 연동과 단체 기능은 개인 링크 관리가 안정화된 뒤 구현한다.

## 인증과 권한

최종 제품에서는 로그인한 사용자만 링크를 생성하거나 관리할 수 있다. 조회와
목적지 이동은 로그인 없이 가능하다.

- 개인 링크: 생성자 또는 위임받은 사용자만 관리
- 단체 링크: 단체 관리자만 관리
- 생성자와 현재 소유자를 구분해 감사 가능하게 저장
- 링크 및 단체 이관은 이력을 남기고 되돌릴 수 있게 설계

현재 MVP는 인증 전 흐름을 검증하기 위해 모든 링크를 임시 사용자 `0`으로
저장한다. 이는 최종 정책이 아니다.

## 신고와 안전

- 확인 페이지에서 목적지 도메인을 명확히 표시
- 링크 신고 진입점 제공
- 피싱, 악성코드, 사칭, 불법 콘텐츠 등 신고 사유 분류
- 신고 누적 또는 운영자 판단에 따른 비활성화
- 비활성 링크에는 목적지 대신 차단 사유 안내
- 링크 생성 시 내부 네트워크 주소와 인증정보가 포함된 URL 차단

신고 처리 절차와 운영 권한은 SPARCS 운영 정책과 함께 확정한다.

## 시스템 구성

```text
apps/web            Next.js 웹, 관리 화면, /[slug] 목적지 확인 페이지
apps/api            NestJS 링크 API
packages/contracts  Zod 요청·응답 계약
packages/config     ESLint·TypeScript 공통 설정
MySQL               링크, 소유권, 설정의 원본 저장소
Redis               조회 캐시, 요청 제한, 향후 분산 락
```

- 패키지 관리: pnpm
- 모노레포 실행: Turborepo
- ORM: MikroORM
- 데이터베이스: MySQL
- 캐시 및 동시성 제어: Redis
- 단체 연동: gRPC, 향후 필요 시 gRPC Gateway

링크 조회 Redis TTL은 현재 120초다. 로컬 인메모리 캐시는 운영 복잡도에 비해
효과가 확인되지 않아 사용하지 않는다. 링크 변경 기능을 구현할 때 DB 반영 후
Redis를 무효화하고, 완료된 시점에 관리 화면의 상태를 `반영 완료`로 바꾼다.

## 배포 환경변수

- `PUBLIC_WEB_ORIGIN`: 기본 공개 주소
- `ALTERNATE_WEB_ORIGIN`: 같은 slug를 제공하는 선택적 보조 주소
- `API_INTERNAL_URL`: Next.js 서버에서 NestJS로 접근하는 내부 주소

공개 주소 환경변수에는 경로 없는 HTTP(S) origin만 허용한다.

## 현재 구현

- pnpm + Turborepo 모노레포
- Next.js 웹과 NestJS API
- MikroORM + MySQL 링크 저장
- 사용자 지정 및 자동 slug 생성
- slug DB unique constraint와 예약어 검증
- Redis 조회 캐시와 장애 시 MySQL fallback
- Redis 기반 익명 생성 요청 제한과 프로세스 내부 fallback
- 내부 네트워크 및 인증정보 포함 URL 생성 차단
- 기본·보조 공개 주소에서 동일 링크 제공
- 목적지 확인 페이지
- Railway 프리뷰 배포

## 구현 순서

1. 로그인, 개인 링크 목록·수정·비활성화, `userId` 소유권
2. Redis 분산 락, QR 생성, 변경 반영 상태
3. 접속 로그·집계와 관리 통계
4. 신고 및 운영자 차단 흐름
5. 링크트리
6. 커스텀 단체, 관리자 및 이관
7. Clubs gRPC 연동과 선택적 gRPC Gateway
